Why Split-Kernel

Isolation Built into the Architecture

In a traditional Linux kernel, application code and device processing compete for the same CPU cores. The split-kernel architecture removes this contention by offloading all device processing to a dedicated kernel on dedicated cores. Applications see zero device interrupts, not because of tuning, but because device interrupts physically cannot reach them.

Benchmarks

Measured on the Same Machine

Same server, same kernel build, one variable at a time: a multikernel instance against a fully accelerated KVM guest, or two kernels against one. Every number links to its setup, caveats, and reproduction steps.

2.5x Faster context switches than KVM 1.37 µs vs 3.42 µs

Against a guest with EPT, APICv, and pinned vCPUs. KVM closes the gap only by spinning its idle cores, at up to 19 W per guest. Multikernel stays fast while sleeping in real C-states.

lmbench vs KVM 10x Less CPU to receive at line rate 21% vs 215% of a core

Both sides hit line rate. The VM paid 2x the CPU to send, 10x to receive, and added four times as much round-trip latency (0.40 ms vs 0.10 ms) through vhost-net.

iperf vs KVM 2.6x More throughput from the same 24 cores 780K vs 300K unlinks/s

Two kernels instead of one, on identical hardware: 2.1x on stat() of a shared file, 4.1x on unlink across sockets. Locks that are not shared are not contended. Control benchmarks moved by at most 1%.

will-it-scale 153x Lower p99 beside a noisy neighbor 232 ms vs 35.6 s

A latency-sensitive task next to a memory-hungry batch job. On one kernel, cgroups protect the victim only by starving the batch job to 10 passes. With two kernels, both run at full speed.

Tail latency 61x Faster large-memory instance setup 111 ms vs 6.81 s, 32 GiB preallocated

QEMU with preallocated RAM spends seconds populating pages before a vCPU runs, and pinning memory for a passthrough device costs the same. Multikernel assigns physical ranges it already owns, in about 110 ms from 1 GiB to 32 GiB.

Instance memory setup 0 Bytes lost across four kernel panics 4 of 4 panics verified intact

An app-kernel panicked mid-write four times. Each time, a fresh kernel booted on the same DAXFS memory and found every byte in place, down to a half-written page. No log replay, no reload.
