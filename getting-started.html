Getting Started with Multikernel

Install the multikernel kernel and the kerf tool, set aside CPUs and memory, and boot your first kernel instance alongside the host.

View on GitHub Learn the Architecture

Overview

Multikernel Linux runs several independent Linux kernels side by side on one machine. Each kernel owns its own CPUs, memory, and assigned devices, and runs directly on the hardware without a hypervisor. This guide takes you from a stock Linux host to a running kernel instance that boots straight into a container image.

The guide uses the following terms:

  • Host kernel: the multikernel-enabled kernel the machine boots. It behaves like a regular Linux kernel and can additionally spawn other kernels.
  • Resource pool: the CPUs, memory, and devices the host sets aside for other kernels.
  • Instance: a named allocation from the pool, together with the kernel loaded into it.
  • Spawned kernel: the kernel running inside an instance, with its own scheduler, network stack, and view of its devices.

Before You Begin

Prebuilt packages are available for x86_64. On other architectures, build the kernel and kerf from source.

Architecture Kernel Kerf
x86_64 deb or rpm package, or source deb or rpm package, PyPI, or source
arm64 Source PyPI or source
RISC-V Source, plus device tree blobs PyPI or source

You also need:

  • Root access. The kerf commands that change kernel state run under sudo.
  • CPUs and memory the host can give up. Everything placed in the resource pool is removed from the host until you release it.
  • A running Docker daemon, if you boot an instance from a container image as this guide does.
  • For source builds: the usual Linux kernel build toolchain, Python 3.8 or later with pip, and musl-gcc for kerf.

1 Install the Multikernel Kernel

The host must boot a kernel built with CONFIG_MULTIKERNEL and CONFIG_MKTTY. Install it from a package or build it from source.

Option A: deb or rpm package (x86_64)

Download the kernel package for your distribution from the releases page, install it, and reboot into the new kernel. The packaged kernel has both options enabled.

# Debian / Ubuntu
sudo apt install ./linux-image-<version>_amd64.deb

# Fedora / RHEL
sudo dnf install ./kernel-<version>.x86_64.rpm

sudo reboot

To build out-of-tree modules such as DAXFS in step 3, also install linux-headers (deb) or kernel-devel (rpm) from the same release.

Option B: build from source

git clone https://github.com/multikernel/linux.git
cd linux
cp /boot/config-$(uname -r) .config  # Start from the running kernel's config
make menuconfig                      # Enable CONFIG_MULTIKERNEL=y and CONFIG_MKTTY=y
make -j$(nproc)
sudo make modules_install
sudo make install
sudo reboot

CONFIG_MULTIKERNEL depends on CONFIG_MEMORY_HOTPLUG, CONFIG_MEMORY_HOTREMOVE, and CONFIG_CONTIG_ALLOC. Enable them first if your starting config lacks them. The kernel uses them to carve out memory for spawned kernels at runtime, so no extra module or boot parameter is needed.

Also enable CONFIG_MULTIKERNEL_VSOCKETS, the vsock transport between kernels. kmorph requires it, and kerf exec in step 6 runs over the same transport.

Additional steps on RISC-V

RISC-V boards boot from a device tree, so build and install the device tree blobs as well. Run these commands after make -j$(nproc) and before rebooting:

make dtbs
sudo make dtbs_install INSTALL_DTBS_PATH=/boot/dtbs/$(make -s kernelrelease)

Set INSTALL_DTBS_PATH to the directory your bootloader loads device trees from.

Verify

After the reboot, confirm that the running kernel has multikernel support:

uname -r
grep -E 'CONFIG_(MULTIKERNEL|MKTTY)=' /boot/config-$(uname -r)

Both options should be reported as =y.

2 Install Kerf

Kerf is the command-line tool that manages the resource pool and the full instance lifecycle: creating instances, loading kernels into them, booting them, and tearing them down.

Option A: deb or rpm package (x86_64)

Download the package from the kerf releases page and install it:

# Debian / Ubuntu
sudo apt install ./kerf_<version>_amd64.deb

# Fedora / RHEL
sudo dnf install ./kerf-<version>.x86_64.rpm

Option B: PyPI

The distribution is named kerf-multikernel; the installed command is kerf.

pip install kerf-multikernel

Option C: build from source

Use this to track the development tree. The build compiles a static kerf-init binary and needs musl-gcc (the musl-tools package on Debian and Ubuntu).

git clone https://github.com/multikernel/kerf.git
cd kerf
sudo pip install .

Verify

kerf --help

Note: the remaining steps run kerf under sudo, so the command must be on root's PATH. A per-user pip install places it in ~/.local/bin, which sudo does not search by default.

3 Load the DAXFS Module

DAXFS is a filesystem shared between kernels through direct memory access. Kerf uses it to hand a container image to a spawned kernel as its root filesystem. It is an out-of-tree kernel module, and kerf does not load it automatically.

git clone https://github.com/multikernel/daxfs.git
cd daxfs
make
sudo insmod daxfs.ko

The spawned kernel needs DAXFS support too: either build it into that kernel, or pass --initrd in step 5 with an initramfs that loads daxfs.ko.

Note: DAXFS is required only to boot from a container image or to share a host directory. An instance that boots conventionally from an initramfs with --initrd alone does not need it, and you can skip this step.

4 Initialize the Resource Pool

The resource pool holds the CPUs and memory that instances are allocated from. The kernel carves the pool out of the running host, so no reboot is required.

# Pool CPUs 4-31 and 8 GB of memory
sudo kerf init --cpus=4-31 --memory=8GB

Adjust the values to your machine, and keep in mind:

  • CPU IDs are physical IDs, not the logical CPU numbers shown by most tools: the APIC ID on x86 and the MPIDR on arm64. On x86, list them with grep -E '^(processor|apicid)' /proc/cpuinfo.
  • Memory given as a plain size is taken from the NUMA node of the requested CPUs. To choose nodes explicitly, write --memory=8GB@0,8GB@1.
  • Devices can be pooled as well, by name or PCI address, for example --devices=nvme0n1,enp9s0.

To preview the result without changing anything, add --dry-run. Running kerf init again with different values reshapes the live pool.

5 Create and Boot an Instance

Launching an instance takes three commands: allocate resources from the pool, load a kernel, and boot it.

# Allocate 4 CPUs and 2 GB of memory from the pool
sudo kerf create web-server --cpus=4-7 --memory=2GB

# Load a kernel that boots straight into a Docker image
sudo kerf load web-server --kernel=/boot/vmlinuz-$(uname -r) --image=nginx:latest

# Boot the instance and attach to its console
sudo kerf start web-server --console

With --image, kerf builds a DAXFS image from the Docker image, and the spawned kernel mounts it directly as its root filesystem. The example loads the same multikernel kernel the host is running; any kernel with CONFIG_MULTIKERNEL works.

The spawned kernel boots on its assigned CPUs and memory and runs directly on the hardware. Its console is mktty0 by default, which --console attaches to. To detach from the console without stopping the instance, press Ctrl+] and then ..

To boot conventionally instead, replace --image with --initrd and pass kernel parameters with --cmdline. Run kerf load --help for the full list of options, including network settings for the instance.

6 Manage the Instance

Once the instance is running, inspect it, run commands inside it, and resize it from the host.

# List all instances, or show one in detail
sudo kerf show
sudo kerf show web-server

# Run a command inside the instance, as with docker exec
sudo kerf exec web-server ls /
sudo kerf exec -it web-server sh

# Resize the running instance
sudo kerf update web-server --memory=4GB

Memory is resized in units of the kernel's memory granule, and kerf refuses a size that is not a multiple of it. Add --dry-run to validate a change without applying it.

Command Purpose
kerf init Create, reshape, or release the resource pool
kerf create Allocate an instance from the pool
kerf load Load a kernel, and optionally an initrd or container image, into an instance
kerf start Boot an instance
kerf exec Run a command inside a running instance
kerf show Show instances and their resources
kerf update Change the CPUs, memory, or devices of an instance
kerf dump Save the pool or an instance as a device tree that kerf init --input and kerf create --input can replay
kerf kill Shut down a running instance
kerf unload Unload the kernel image from an instance
kerf delete Delete an instance and return its resources to the pool

Every command documents its options under kerf <command> --help.

Clean Up

Shut the instance down, remove it, and hand the pooled CPUs and memory back to the host:

sudo kerf kill web-server
sudo kerf unload web-server
sudo kerf delete web-server

# Return all pooled resources to the host
sudo kerf init --cpus=none --memory=none

If an instance does not shut down gracefully, kerf kill --force halts it.
