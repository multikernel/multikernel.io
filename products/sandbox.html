The Problem

AI agents need strong isolation, native performance, and fast lifecycle management. Today's options force a tradeoff.

Containers

Fast to start, but every container shares one kernel and a compromised agent can escape it. GPU passthrough works, but isolation is not sufficient for untrusted code execution.

VMs and MicroVMs

Strong isolation, but microVMs like Firecracker have no GPU passthrough, and full VMs need VFIO with all guest memory pinned and preallocated. Sharing a GPU takes SR-IOV or vGPU. Inside a cloud VM, all of it requires nested virtualization.

Multikernel Sandbox

Each agent gets its own kernel on dedicated cores, driving its GPU with the native driver. Kernel-level sandboxing without a hypervisor, on bare metal or inside the cloud VMs you already run.

Built for AI Workloads

Kernel-Level Isolation

Each agent is sandboxed in its own kernel on its own cores and memory. A compromised agent cannot reach other agents' memory, devices, or kernel state.

Direct GPU Access

Assign a whole GPU to an agent's instance. Its kernel runs the vendor driver against real hardware: no VFIO, no VMM, no vGPU license, even inside a cloud GPU instance.

Shared Model Weights

Load model weights once into DAXFS and every agent instance maps the same physical copy, with zero copies and no per-agent load time. Firecracker has no shared filesystem, so each microVM holds its own copy.

No KVM Required

Runs on bare metal or inside VMs you already rent. No /dev/kvm, no nested virtualization, no special instance types.

Dedicated Cores

Each agent's cores run only its own kernel. No vCPU time-slicing, no steal time, no noisy neighbors between agents.

Fast Instance Creation

Instances draw memory from a prepared physical pool: 32 GiB assigned in 111 ms, with no page population on the launch path.

Crash-Contained Agents

A kernel panic stays inside one agent's instance. Memory on DAXFS survives it intact, so recovery is a kernel boot, not a cold start.

Docker Compatible

Deploy agents using your existing Docker images and workflows. No new packaging format, no new APIs.

Defense in Depth

Sandlock on Top, Multikernel Underneath

Multikernel draws the boundary between agents: each one gets its own kernel, cores, and memory. Sandlock draws the boundary inside an agent: every tool call, shell command, or generated script runs in its own lightweight process sandbox, confined by Landlock and seccomp, with network egress denied by default.

A compromised tool has to escape Sandlock to reach the rest of its agent, then escape the agent's kernel to reach anyone else. Sandlock starts in about 5 ms and needs no root, containers, or hypervisor, so the inner layer adds almost nothing to each call.
